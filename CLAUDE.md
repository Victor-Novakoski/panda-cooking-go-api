# Panda Cooking — API

API REST de uma rede de receitas (cadastro, receitas com fotos, busca sem acento, comentários e favoritos). Projeto de portfólio; o front em Next.js está em `panda-cooking-front`.

## Stack

Go 1.26 · Gin · GORM com migrations em SQL (golang-migrate, embutidas no binário) · PostgreSQL 16 (`unaccent` + `pg_trgm`) · JWT HS256 + refresh token em cookie · `log/slog` · testify, mocks à mão, testcontainers · OpenAPI 3 escrito à mão.

## Comandos

```bash
cp .env.example .env && docker compose up --build   # banco, API (air) e front, com o front clonado ao lado
make test              # unidade e HTTP, com -race (igual à CI)
make test-integration  # contra um Postgres de verdade (build tag integration)
make lint              # golangci-lint, mesma configuração da CI
make seed              # APAGA o banco e recria os dados de demonstração
```

O compose fica aqui; o front é montado de `../panda-cooking-front` (ou `FRONT_DIR`) e usa `API_URL=http://api:8080` no servidor. Postgres em `127.0.0.1:5433`. `SECRET_KEY` precisa de 32+ caracteres, e com `APP_ENV=production` a chave do `.env.example` é recusada.

## Como se orientar

- Leia `docs/INDEX.md` e abra só o que a tarefa pede.
- Rotas, corpos e respostas: `api/openapi.yaml` (é a fonte; não há tabela de rotas escrita à mão).
- Convenções da API (erros, status, paginação, cookies): `docs/DESIGN.md`.
- Tarefas abertas são issues do GitHub. Os repos antigos da org Panda-Cooking (2023) são só referência.

## Regras gerais

- Escopo: uma tarefa por vez, ligada a uma issue. O que aparecer no caminho vira issue nova, não entra de carona. Nada de dependência ou camada "para o futuro".
- Camadas: handler só fala HTTP, regra de negócio no service, banco só no repository. Detalhes no `CLAUDE.md` de cada pasta em `internal/`.
- Identificadores em inglês; comentários, docs, mensagens de erro e commits em português.
- Segredos só em variável de ambiente; valor novo vai para o `.env.example` com placeholder. **Nenhuma senha escrita em docs**, nem de teste ou de demonstração: diga onde ela é definida.
- Repositório público: nada de código, nome de cliente ou padrão interno de outra empresa.

## Checklist de segurança (toda mudança)

- [ ] Entrada validada no back-end, com tamanho máximo, mesmo que o front já valide.
- [ ] Rota nova com autenticação e papel explícitos; rota pública é exceção justificada.
- [ ] Recurso acessado por id confere o dono (IDOR).
- [ ] Resposta sem hash, token, dado pessoal desnecessário ou detalhe interno de erro.
- [ ] Nenhum segredo no código, em log ou em commit.
- [ ] Dependência nova necessária, mantida e limpa no `govulncheck`.

Como cada risco é tratado: `docs/SECURITY.md`.

## Testes

- Regra de negócio nova: teste no service. Rota nova: teste do handler (status e corpo).
- Consulta nova, transação, busca ou cascata: teste em `internal/integration`.
- Bug corrigido ganha um teste que falhava antes.

## Git e PR

- Trabalhar a partir da `develop`; tudo entra por PR, nunca push direto na `main` ou na `develop`. Branches são apagadas depois do merge.
- O Victor faz os merges: squash na `develop`; `develop` → `main` sempre com merge commit.
- Conventional Commits em português, assunto em minúsculas (`feat: busca por ingrediente`). O título do PR segue o mesmo formato (a CI confere, porque o squash usa o título).
- Commits com a identidade do Victor, sem linha de atribuição de IA. Um assunto por commit; nunca commitar `.env` nem binários.
- A integração do GitHub põe sozinha um rodapé "Generated by Claude Code" na descrição do PR (e o recoloca ao editar). Remover; se voltar, só dá para tirar à mão.
- A CI roda em PR e em push para `develop` e `main`.

**Pronto** = sobe com `docker compose up`, tem testes, lint limpo, checklist revisado, OpenAPI e docs atualizados e a issue fechada.

## Na nuvem (Claude Code)

- Nunca use `pkill -f` com um padrão que aparece no próprio comando bash (mata o shell). Use `pkill -x api` ou `kill <pid>`, e mate os processos da API que sobrarem depois dos testes.
- Não há Docker: `make test-integration` precisa de `TEST_DATABASE_URL` (ver `internal/integration/CLAUDE.md`).

## Manutenção dos docs

- Antes de uma tarefa, leia docs/INDEX.md e abra só o que ela pede.
- Ao terminar, se aprendeu algo não documentado que faria falta, registre no CLAUDE.md do módulo.
- Doc passou de ~150 linhas? Divida por subtema e atualize o INDEX.
- Decisão de arquitetura nova → arquivo novo em docs/decisoes/.
- Se o código contradiz o doc, o código vale: corrija o doc e avise.
